> 원본: Gonfluence GIRA › 개발문서 › Gira·Gonfluence 알파 명세서 (http://172.21.1.1:3001/s/GIRA/p/1000000000009), 버전 15

## 개요

알파 버전의 목표는 PoC(검증용 단일 사용자 환경)를 **사내 100명이 실제 업무에 쓸 수 있는 시스템**으로 올리는 것이다. PoC에서 이미 검증된 것: Jira 이슈 이관(NEXT·SIMSIM, 약 6,100건)과 백로그·보드·JQL·다크모드, Confluence 4개 스페이스 1,066페이지 이관과 보기·편집·홈 화면.

알파에서 새로 들어가는 축은 네 가지다.

1. **운영 기반** — Gira/Gonfluence 분리, 100명 규모 설계, Docker 배포
2. **조직·권한** — 팀/그룹, 역할(시스템 관리자·팀장·파트장·PM), 프로젝트 접근 제어, 권한 요청
3. **개방성** — 내보내기/가져오기, API Key와 REST API, 모바일 보기
4. **품질·지원** — Gonfluence 편집기 고도화, AI 연계 도움말, 피드백의 Gira 자동 등록, MS Entra SSO(마지막)

## 시스템

### Gira / Gonfluence 분리

현재는 한 저장소·한 PostgreSQL에 두 앱이 있고 `users` 테이블만 공유한다(jira_* FK 7개가 users 참조). 알파에서는 서비스 단위로 분리한다.

- **DB 분리**: `pg_dump --table 'jira_*'`로 Gira DB를 따로 만들고 `users`는 양쪽에 복제. 사용자 정보의 원본(source of truth)은 인증 쪽 한 곳으로 정하고, 다른 쪽은 동기화(추후 Entra 연동 시 자동 해결).
- **코드 분리**: 서버는 이미 별개 프로세스(3001/3002)라 경계가 분명하다. 저장소는 모노레포 유지 + 배포 단위 분리를 기본안으로 하되, 완전 분리(저장소 2개)는 선택지로 남긴다.
- **앱 간 연결**: Gonfluence 페이지의 Gira 이슈 링크, Gira에서 문서 링크는 URL 기반으로 유지(DB 직접 참조 제거).

### 관리 컴포넌트 분리

사용자·팀·그룹·직책 관리(전역 권한)는 별도 **관리 컴포넌트**로 분리해 조직 데이터의 단일 원본으로 삼는다.

- 배포 조합: **Gira + Gonfluence + 관리** / **Gira + 관리** / **Gonfluence + 관리** — 어떤 조합이든 관리는 항상 포함된다.
- 관리가 조직 DB(users/teams/groups/직책/생성 권한 그룹)를 소유하고, Gira/Gonfluence는 같은 스택의 조직 DB를 참조한다(읽기) — 현재의 DB 간 미러링은 이 구조로 대체.
- 리소스별 권한 부여(어느 팀이 어느 프로젝트/스페이스에 접근하는가)는 각 앱 DB에 남는다 — 앱 단독 백업/이동이 유지된다.
- 사용자·팀·그룹 관리 화면은 관리 컴포넌트 UI(3003)로 일원화한다. 접근 요청 승인함은 요청 데이터가 있는 각 앱에 남는다. Entra 연동(OIDC)은 관리 컴포넌트가 담당한다.

### 100명 규모 설계

| 항목 | 현재(PoC) | 알파 목표 |
| --- | --- | --- |
| 동시 사용자 | 1명 | 동시 접속 ~30명, 계정 100명 |
| 응답 | 미측정 | 주요 화면 p95 < 1초 |
| 서버 | Node 단일 프로세스 수동 실행 | Docker 컨테이너, 재시작 자동화 |
| 세션 | 메모리/쿠키 | DB 또는 Redis 기반 세션 저장 |
| 첨부 | 로컬 디스크 | 전용 볼륨(전체 이관 시 약 102 GiB) + 백업 |
| DB | 인덱스 일부 | 슬로우 쿼리 점검, 커넥션 풀 상한 설정 |

### Docker 배포

- 앱별 독립 스택 2개(`docker/docker-compose.gira.yml` / `docker/docker-compose.gonfluence.yml`, Docker 파일은 `docker/` 폴더에 모음) — 각자 postgres를 갖고 따로 배포·재배포한다. 같은 호스트든 다른 호스트든 무방하며, TLS는 앞단 리버스 프록시에서 처리한다.
- 정적 빌드(web/dist, dist-jira-app)는 이미지 빌드 단계에 포함.
- 비밀 값은 `.env` 파일 주입, 이미지에 포함 금지.
- 배포 대상: 사내 TrueNAS 서버. DB 데일리 백업(pg_dump) + 첨부 볼륨 스냅샷.

## 관리 (조직·권한)

조직은 세 축으로 반영한다: **직급**(표시용), **직책**(권한 판정에 사용), **그룹**(수평 조직). Gira와 Gonfluence가 같은 모델을 쓴다.

### 팀·그룹

- **팀·파트**: 팀 아래 파트가 있는 2단 조직. 사람은 주 소속 파트(또는 팀 직속) 하나를 가지며, 겸직 등 추가 소속은 그룹으로 처리한다.
- **직책**: 팀장 / 파트장 / 파트원 — 권한 판정에 쓰는 값.
- **직급**: 임원(대표이사·부사장·전무·상무·이사…)·책임매니저·책임연구원 등 — 표시용이며 권한에 직접 쓰지 않는다. "임원 전체 열람" 같은 정책은 '임원' 그룹에 권한을 주는 식으로 해결한다.
- **그룹**: 수평 조직(임원, 개발프로젝트, PM들, 기획 등). 한 사람이 여러 그룹에 속할 수 있다.
- **프로필 이미지**: 개인이 설정 › 프로필에서 직접 등록·변경·삭제한다(가운데 정사각형으로 잘라 256×256 축소, PNG·JPEG). 등록 이미지는 조직 데이터(users.avatar_key, user_avatars)로 관리 서비스가 저장·복제해 Gira·Gonfluence에 함께 보이고, 없으면 Entra 계정 사진 → 기본 이니셜 순으로 표시한다.
- **접근 부여 대상(principal)**: 팀 / 파트 / 그룹 / 개인 — 네 종류.

### 역할과 권한

| 권한 | 누가 가지나 | 할 수 있는 것 |
| --- | --- | --- |
| 시스템 관리자 | 명시 지정(복수 가능) | 사용자·팀·그룹 관리, 전역 설정, 모든 리소스 접근·승인, 내보내기/가져오기 |
| 생성 권한 | 팀장·파트장 직책 + 지정 그룹(PM들 등). 일반 구성원은 개인 스페이스 1개만 생성 가능 | 프로젝트/스페이스 생성 — 생성자는 그 리소스의 관리자가 된다 |
| 리소스 관리자 | 생성자 + 추가 지정 | 해당 프로젝트/스페이스의 접근 범위 지정·변경, 권한 요청 승인, 멤버 역할 관리 |
| 일반 구성원 | 접근 범위에 포함된 사람 | 부여된 등급(보기/편집)으로 이슈·문서 작성·편집 |

PM은 별도 직책이 아니라 'PM들' 그룹으로 다룬다 — 생성 권한을 주는 그룹 목록은 시스템 관리자가 설정에서 관리한다.

### 프로젝트 생성과 접근 범위

프로젝트(Gira)·스페이스(Gonfluence) 생성 시 접근 가능한 대상을 지정한다: 전사 공개 / 특정 팀 / 특정 파트 / 특정 그룹 / 개인 지정. 접근 등급은 보기·편집·관리 3단계.

스페이스는 대표 이미지(아이콘)를 선택할 수 있다 — 생성 화면에서 PNG·JPG·WebP 1MB 이하 파일을 올리며, 사이드바·홈 스페이스 목록에 정사각형 아이콘으로 표시된다. 올리지 않으면 기존 색상 상자와 이름 첫 글자를 유지하고, 스페이스 관리자는 설정 › 스페이스 이미지에서 바꾸거나 지울 수 있다.

이관된 기존 데이터는 **기본 비공개**로 전환한다. 시스템 관리자가 스페이스/프로젝트마다 접근 팀을 지정하면, 지정된 팀의 팀장(또는 함께 지정된 권한자)이 그 리소스의 관리자로서 세부 권한을 설정한다. 지정되지 않은 사용자는 접근 권한 요청으로 들어옵다.

정말 민감한 데이터는 한 단계 더 격리할 수 있다: 공용 인스턴스에 올리지 않고, 원본 Jira/Confluence에서 프로젝트·스페이스 단위로 **별도 비공개 인스턴스**(독립 도커 스택)에만 이관해 그곳에서 운영한다. 이관 도구가 프로젝트/스페이스 단위 선택을 지원하고 배포가 앱별 독립 스택이므로 추가 개발 없이 가능하다.

접근 제어 단위는 세 층이다: 프로젝트/스페이스 단위가 기본이고, **개별 문서(페이지) 단위 제한**도 가능하다 — 보기 제한은 하위 페이지에 상속되고, 편집 제한은 해당 문서에만 적용된다(Confluence와 동일). 부여 대상은 모든 층에서 동일(팀/파트/그룹/개인)하다.

### 접근 권한 요청

1. 권한 없는 사용자가 이슈/문서 링크를 열면 "접근 권한 요청" 화면을 본다(제목·내용은 노출하지 않음).
2. 요청 사유를 적어 제출하면 해당 프로젝트/스페이스의 관리 권한자에게 알림이 간다.
3. 승인 시 보기 또는 편집 권한이 부여되고 요청자에게 알림, 거절 시 사유와 함께 알림.
4. 요청·승인 이력은 감사 로그로 남긴다.

## 도움말: AI 연계

도움말 메뉴에서 사용법을 자연어로 묻고 답을 받는다. 정적 도움말 문서 대신 **사용 안내 프롬프트 + LLM API** 구성으로 만든다.

- 서버가 LLM API를 호출하고(API Key는 서버 `.env`), 기능 설명·단축키·권한 규칙 등을 담은 시스템 프롬프트를 관리자가 편집할 수 있다.
- 현재 보는 화면(백로그/보드/편집기 등)을 컨텍스트로 함께 보내 "지금 이 화면에서 어떻게 하나요" 질문에 답한다.
- 문서·이슈 내용 자체를 AI에 보내는 것은 알파 범위 밖(보안 검토 필요). 사용법 질문만 다룬다.
- 사용할 모델과 비용 한도는 미결 사항 참조.
- **현재 구현(알파, GIRA-15)**: 상단 ?(도움말)로 여는 오른쪽 패널. 지금 화면(앱·주소·화면 이름)을 함께 보내고, 개발참여 챗봇과 같은 키·모델(effort low)을 쓴다. 지침은 저장소 기본 안내 + 사이트 관리자가 설정 › 'AI 도움말 지침'에서 고친 판. 사용량은 ai_usage에 기록하고 사용자별 하루 상한(AI_DAILY_LIMIT, 기본 30회)을 둔다.

### AI 검색 (Gira)

목록 필터 줄의 'AI'에서 자연어로 조건을 말하면("2026년에 완료 처리한 이슈, 중복·닫음 제외") AI가 JQL로 바꿔 현재 프로젝트 목록에 적용하고 건수를 보여 준다(Jira Rovo 검색에 대응).

- 모델에는 질문·오늘 날짜·필드와 실제 값 목록(상태·해결 상태·유형·우선순위·버전·스프린트·담당자 이름 등)만 보낸다. 이슈 데이터는 보내지 않고, 실제 검색은 기존 JQL 엔진이 사용자 권한 안에서 한다.
- 만든 JQL은 서버 파서로 검사하고(틀리면 한 번 고쳐 받음), 해석·가정(예: '닫음' → 상태 '닫음')을 함께 보여 준다. JQL은 입력칸에 남아 고쳐 쓰거나 필터로 저장할 수 있다.
- 사용량·상한은 도움말과 같다. 담당자별·월별 같은 집계 표는 아직 없다(그룹화로 대신).

## 의견·버그 리포트

모든 화면에 "의견 보내기" 진입점을 두고, 제출된 내용은 **Gira의 전용 프로젝트에 이슈로 자동 등록**한다.

- 자동 첨부: 제출 화면 URL, 브라우저·OS 정보, 앱 버전, (선택) 스크린샷.
- 자동 처리: 유형(버그/개선 요청) 분류, 유사 이슈 중복 감지, 담당자 자동 배정 규칙. 1차는 규칙 기반으로 하고, AI 분류는 도움말 AI 연계와 같은 경로를 재사용한다.
- 제출자에게 등록된 이슈 키를 보여주고, 처리 상태 변경 시 알림을 보낸다.

### 공동 개발 모델 (구현됨: 개발참여)

이 시스템 자체를 공동 개발로 키운다. 양 앱 좌측 메뉴의 **개발참여**에서 신규 기능·수정 요청·버그를 입력하면 Gira의 **GIRA 개발 프로젝트**에 이슈로 등록된다 (개발 명세서 링크 포함).

- 등록은 로그인한 누구나, GIRA 프로젝트 열람·처리는 '팀장' 그룹으로 한정 (추후 확대).
- Gonfluence 입력은 서비스 키로 Gira에 프록시되며 작성자·출처가 설명에 남는다.
- **처리 파이프라인(구현)**: 개발참여 챗봇(Claude API)은 요청을 해석해 **이슈 등록까지만** 한다 — 첨부(스크린샷·로그) 가능, 명세서 범위를 넘으면 needs-approval. 처리는 개발 세션(Claude Code)이 이슈를 읽고 직접 구현하거나 codex/opencode 헤드리스에 맡긴다: 사람이 지시할 때와 매일 04:17(KST) 시스템 cron 자동 확인(우선순위 순, 1회 최대 3건). 이슈마다 feature/<키> 브랜치 → GitHub PR, 머지·서버 반영은 사람이 검토 후 지시. 진행은 이슈 상태(진행 중 → 검토)와 댓글로 남는다.
- 코드는 GitHub 공동 저장소(gmdsoft/gira)에서 관리한다 — 양 앱 메뉴의 '저장소' 바로가기.

## 알림·외부 연동

활동이 일어날 때(이슈 생성·상태 변경·내용 업데이트·댓글, 문서 생성·수정·댓글) 지정된 채널로 알린다.

- **발송 옵션**: ① Teams 채널 게시(채널 Incoming Webhook URL 등록) ② 메일(담당자·보고자·지정 주소) ③ 인앱 알림(종 아이콘)
- **설정 단위**: 프로젝트/스페이스별로 "어떤 이벤트를 어디로" 규칙을 리소스 관리자가 지정한다. 개인은 내 관련 이벤트(내 담당 이슈 등)의 수신 여부를 설정한다.
- **구현**: 서버에서 이벤트 발생 시 규칙 매칭 → 발송 큐(실패 재시도). SMTP 주소와 Teams 웹훅은 관리 설정에 둔다. 알림 내용에는 제목·링크만 담고 본문은 담지 않는다(권한 밖 노출 방지).
- 구현 순서상 4단계(품질·지원)에 포함한다.
- **현재 구현(알파, GIRA-14)**: 이벤트는 이슈 생성·상태 변경·이슈 댓글(Gira), 문서 생성·수정·댓글(Gonfluence). 규칙은 프로젝트/스페이스 관리자가 설정 › 알림에서 정한다(이벤트 · Teams 채널 웹훅 또는 메일 · 받는 사람: 주소, @assignee·@reporter·@author). 발송 큐는 실패 시 최대 5회 재시도(점점 간격을 늘림), 최근 발송 결과를 같은 화면에서 본다. 인앱 알림은 상단 종 — 담당자·보고자(이슈), 작성자·소유자(문서)에게 가고 행동한 사람은 제외. Teams는 채널 웹훅(기본 `TEAMS_WEBHOOK_URL` 또는 규칙별 주소, Microsoft 웹훅 호스트만 허용), 메일은 Microsoft Graph 앱 토큰(`TEAMS_TENANT_ID`·`TEAMS_APP_CLIENT_ID`·`TEAMS_APP_CLIENT_SECRET`·`TEAMS_SENDER_EMAIL`) — 앱 등록에 Mail.Send(애플리케이션) 권한이 있어야 실제로 나간다. 개인별 수신 설정(끄기)은 아직 없다.

## 내보내기 / 가져오기

권한 있는 사용자(시스템 관리자, 팀장)만 실행할 수 있다. 단위는 Gira는 프로젝트, Gonfluence는 스페이스다.

| 방향 | 형식 | 비고 |
| --- | --- | --- |
| 가져오기 | Jira Cloud (API) | PoC 임포터 존재(scripts/jira-import-project.mjs) — 관리 화면으로 노출 |
| 가져오기 | Confluence Cloud (API) | PoC 이관 파이프라인 존재 — 관리 화면으로 노출 |
| 내보내기 | Gira 프로젝트 패키지 (zip: JSON + 첨부) | 신규 — 자체 형식 정의 필요 |
| 가져오기 | Gira 프로젝트 패키지 | 신규 — 내보내기와 쌍, 인스턴스 간 이동 지원 |
| 내보내기 | Gonfluence 스페이스 패키지 (zip: 문서 JSON + 첨부) | 신규 |
| 가져오기 | Gonfluence 스페이스 패키지 | 신규 |

자체 형식은 문서 본문(변환된 doc JSON)·버전 이력·첨부·메타(작성자, 일시)를 포함하고, 사용자 매핑은 이메일 기준으로 한다. 대용량(수 GiB 첨부)은 백그라운드 작업 + 진행률 표시로 처리한다.

### 팀장 셀프 이관 (운영 전 온보딩)

시스템 운영 전, 권한을 받은 각 팀장이 직접 자기 팀 데이터를 옮기는 화면을 제공한다.

1. 팀장이 자신의 Atlassian API 토큰을 등록한다 (서버에는 암호화 저장, 이관 완료 후 삭제 가능).
2. 원본 Jira 프로젝트(전부 옮겨도 무방)·Confluence 스페이스 목록에서 옮길 대상을 선택한다.
3. 이관은 백그라운드로 진행되고 진행률·결과(성공/실패 항목)을 화면에서 확인한다.
4. 완료되면 이관한 팀장이 해당 프로젝트/스페이스의 리소스 관리자가 된다 (기본 비공개 정책 적용).

일반 구성원(생성 권한 없음)도 **본인 개인 스페이스**(~계정)는 직접 가져올 수 있다 — 이 경우 원본 목록에는 본인 개인 스페이스만 보인다. 팀 단위 프로젝트/스페이스는 종전대로 생성 권한자만 가져온다.

원본 API 호출은 읽기 전용(GET)으로 제한한다 — 원본 Jira/Confluence는 절대 변경하지 않는다.

### 병행 운영기 동기화

실제 Jira/Confluence 사용 중단(컷오버) 전까지는 두 시스템이 병행 운영된다. 이 기간 동안 이미 이관된 프로젝트/스페이스를 원본과 주기적으로 동기화한다.

- **설정**: 리소스 관리자가 동기화 켬/끔과 주기(예: 1시간 / 6시간 / 하루 1회)를 지정. "지금 동기화" 수동 실행과 마지막 동기화 시각·결과도 표시한다.
- **방식**: 원본 updated 시각 기준 증분 수집(변경·신규 이슈/페이지만 재이관, 읽기 전용 GET). 셀프 이관과 같은 토큰을 쓴다.
- **충돌 규칙(제안)**: 병행기에는 원본이 기준 — 양쪽에서 같은 항목이 바뀌면 원본으로 덮고 로그에 남긴다. 이쪽에서만 만든 신규 항목(로컬 생성 이슈·페이지)은 유지한다. 혼란을 줄이려면 병행기 동안 해당 리소스는 원본에서만 편집하도록 안내한다.
- **컷오버**: 동기화를 끄고 원본을 읽기 전용으로 남긴다. 이후 원본 링크 재작성 배치를 실행한다.

**현재 구현(알파)**: 원본 → Gira/Gonfluence **단방향**. 매일 03:00(KST) 이관된 모든 프로젝트·스페이스를 증분 동기화한다(서버 내장 스케줄러, 원본 호출은 GET만, 관리자 API로 상태 조회·즉시 실행). 로컬에서 만든 항목은 원본과 겹치지 않는 번호 대역(1조 이상)을 써서 덮이지 않고 유지된다. 리소스별 켬/끔·주기 설정 화면과 셀프 이관 토큰 사용은 남은 일.

### 원본 링크 재작성

이관 후, 모든 프로젝트·스페이스 내용(문서 본문, 이슈 설명·댓글)에서 기존 Jira/Confluence를 가리키는 링크를 찾아 이관된 시스템 내 링크로 바꾼다.

- 대상이 이관되어 있으면: 새 링크를 추가하고 **기존 링크는 취소선으로 남긴다** (원본 추적 가능).
- 대상이 아직 이관되지 않았으면: 그대로 두고 미해결 목록에 올린다 (나중에 이관되면 재실행).
- 일괄 배치로 실행하고 변경 리포트(어느 문서의 어떤 링크를 바꿨는지)를 남긴다. 재실행 가능(멱등).
- 대상 패턴: 이슈 링크(/browse/KEY), 문서 링크(/wiki/… 형식 전종), 첨부 링크.

## 시스템 백업·복원

장애·실수·서버 교체에 대비해 **시스템 전체**를 정기 백업하고 다른 서버에도 되살릴 수 있게 한다. 콘텐츠 단위로 옮기는 내보내기/가져오기(프로젝트·스페이스 패키지)와는 목적이 다르다 — 이쪽은 재해 복구용이다.

- **대상**: 앱별 DB 전부(Gonfluence·Gira·관리), 첨부 파일 볼륨, 서버 설정(`.env`는 비밀 값이므로 따로 암호화 보관). 검색 색인은 백업하지 않고 복원 후 다시 만든다.
- **백업**: 매일 자동(기본 새벽, 원본 동기화·일일 처리와 겹치지 않는 시각) + 관리 화면의 '지금 백업'. DB는 일관된 시점의 덤프, 첨부는 증분(바뀐 파일만).
- **보관**: 일 7개·주 4개·월 6개를 기본으로 하는 보관 정책, 오래된 것은 자동 삭제. 보관 위치는 앱 서버와 다른 디스크(TrueNAS 다른 볼륨 또는 외부 저장소), 백업 파일은 암호화.
- **복원**: 관리 화면에서 백업 시점을 골라 전체 또는 앱 단위로 복원. 복원 전 현재 상태를 자동으로 한 번 더 백업하고, 복원 중에는 쓰기를 막는다(점검 모드). 빈 서버에 새로 설치한 뒤 백업 파일로 되살리는 절차도 문서로 둔다.
- **확인**: 백업마다 성공·크기·소요 시간을 기록하고, 실패하면 시스템 관리자에게 알린다(알림 연동). 분기마다 별도 환경에 복원 리허설을 해 실제로 되살아나는지 검증한다.
- 관리 화면은 관리 서비스(3003)에 둔다. 시스템 관리자만 실행할 수 있고 실행 이력을 남긴다.

## API

외부 도구(스크립트, CI, 타 시스템)에서 이슈·문서를 다룰 수 있는 REST API를 제공한다. 상세 스펙은 알파 기간 중 별도 문서(OpenAPI)로 확정한다.

### API Key

- 사용자가 개인 설정에서 Key 발급·회수. 발급 시 1회만 표시하고 서버에는 해시만 저장.
- Key의 권한은 발급한 사용자의 권한을 그대로 따른다(별도 scope는 알파 이후).
- 요청 헤더 `Authorization: Bearer <key>`, 호출 이력 로깅.

### 엔드포인트 초안

| 영역 | 예시 | 비고 |
| --- | --- | --- |
| Gira 이슈 | GET/POST /api/v1/issues, GET/PUT /api/v1/issues/{key}, POST 코멘트·상태 전환 | 현재 내부 API를 v1로 정리·고정 |
| Gira 검색 | GET /api/v1/search?jql= | JQL 파서 재사용 |
| Gonfluence 문서 | GET/POST /api/v1/pages, GET/PUT /api/v1/pages/{id}, 첨부 업로드 | 본문은 저장 형식(doc JSON) 또는 Markdown 입력 — 구현됨, 상세는 저장소 docs/api-v1.md |
| 공통 | GET /api/v1/users, 팀/그룹 조회 | 관리자 Key 전용 |

버전 접두사 `/api/v1/`로 고정해 이후 호환성을 보장하고, 기존 화면용 내부 API와는 분리해 운영한다.

## Gonfluence 고도화

### 편집기

구현됨: 기본 서식·목록·정렬·글자색(8색), 표 삽입(크기 선택)·열 너비 드래그·행/열 추가 삭제·병합/분할·헤더 행(상단 툴바에서만), 이미지 붙여넣기·드래그 업로드, 링크·문서/이슈 카드, 목차, 상태, 날짜, 정보/주의 패널, 펼치기, 코드 블록(언어 강조·접기), 레이아웃 2·3단, `/` 명령, 블록 끌어 옮기기, 마크다운 자동 서식(`#` `*` `1.` `[]` `>` `---` ````` `**` `_` ``` `~~`), 편집 중 사이드바, 편집 경고·충돌 경고. 실시간 공동 편집은 알파 범위 밖.

**고도화 목표 (Confluence Cloud 편집기 기준, 2026-11-06 조사)** — 동작·배치는 Confluence를 따르고 코드·에셋은 복사하지 않는다.

#### 1) 표 — 플로팅 표 도구 모음과 셀 메뉴

- 셀에 커서가 있으면 표 바로 아래 가운데에 **표 도구 모음**: '표 옵션 ∨'(헤더 행·헤더 열·번호가 매겨진 행·고정된 열 너비 체크), '정렬 ∨'(표를 왼쪽/가운데에), '열 균등 맞춤', '콘텐츠에 맞춤', '⋯'(복사·삭제). 상단 툴바의 표 버튼 묶음은 이것으로 옮긴다.
- 커서가 있는 셀 오른쪽 위 **'∨' 셀 옵션**(Shift+F10): 배경색 ›(30색), 정렬 ›(세로: 상단·중간·하단), 오른쪽에 열 추가(Ctrl+Alt+→), 아래에 행 추가(Ctrl+Alt+↓), 셀 지우기, 열 삭제, 행 삭제. 여러 셀을 끌어 선택하면 **셀 병합**·열 균등 맞춤이 추가되고, 병합된 셀에서는 **셀 나누기**가 나온다.
- 헤더 열·번호 매긴 행·셀 배경색·세로 정렬은 문서 모델(속성)과 보기 렌더·변환기 모두에 반영한다(원본 Confluence 표 속성과 일치).

#### 2) 표 — 행·열 핸들과 삽입 점

- 행 왼쪽 가장자리 ⠿ **행 핸들**: 누르면 행 전체 선택 + 메뉴(번호가 매겨진 행 토글, 배경색, 위에/아래에 행 추가, 행을 위로/아래로 이동, 셀 지우기, 행 삭제).
- 열 위쪽 가장자리 **열 핸들**: 열 전체 선택 + 메뉴(배경색, 오름차순/내림차순 정렬, 왼쪽에/오른쪽에 열 추가, 열을 왼쪽/오른쪽으로 이동, 셀 지우기, 열 삭제).
- 행·열 경계에 마우스를 올리면 파란 **'+' 삽입 점**과 안내선 — 누르면 그 자리에 행/열 삽입. 열을 넣어도 표 폭은 유지하고 열 너비를 다시 나눈다.
- 단축키: Ctrl+Alt+화살표(행·열 추가), 마지막 셀 Tab = 새 행(구현됨). 핸들 끌어 순서 바꾸기는 후순위.

#### 3) 표 — 폭 넓히기

- 표 오른쪽 가장자리 **세로 막대 핸들**을 끌어 표 폭을 넓히고 줄인다(가운데 기준으로 양쪽으로, 최대 편집 영역 폭). 본문 폭(760px)보다 넓은 표는 본문 밖으로 돌출(breakout).

- '콘텐츠에 맞춤'(내용 기준으로 열·표 폭 축소), '열 균등 맞춤', '고정된 열 너비'(창이 좁아져도 열 너비 유지) 옵션.

### 데이터베이스·화이트보드 원본 데이터 받기

공개 REST v2는 둘 다 메타정보(제목·부모·작성자)만 주고 본문이 비어 있다. 원본 화면은 내부 협업 서비스에서 Yjs 문서 스냅샷을 받아 그린다. 임포터도 같은 경로를 **GET만으로** 쓸 수 있음을 확인했다(81개 모두 성공).

1. `GET /wiki/rest/internal/1.0/canvas/session/bulk?ids=<콘텐츠 id>` (API 토큰) → 접근 토큰·media 토큰
2. `GET /wiki/rest/api/content/<id>` → referenceId
3. `GET /gateway/api/canvas-tenant-context/site/<cloudId>/api/_internal/collab/<ari>?skipSteps=true&v=2` (헤더 `x-access-token`) → Yjs 스냅샷(최신). ari는 화이트보드 = referenceId, 데이터베이스 = `ari:cloud:canvas:<cloudId>:database/<referenceId>`.
4. 파일·이미지는 media 토큰으로 api.media.atlassian.com에서 받는다.

내부 API라 예고 없이 바뀔 수 있으므로, 이관 때 원본 Yjs 바이너리도 함께 보관해 나중에 다시 풀 수 있게 한다.

- **데이터베이스**: fbi(필드 정의 — 이름·형식·선택지), ebi(항목별 셀), vbi(보기 — 표 84·카드 3·보드 3, 필터·정렬·숨김 열). 필드 형식은 텍스트·선택·날짜·숫자·사용자·링크·파일·Jira 이슈·Jira 필드(연결 이슈의 값을 그때그때 표시)·페이지 링크. 우리 쪽은 Jira 필드를 Gira 이슈 값으로 채운다.
- **화이트보드**: board(요소: 도형·텍스트·커넥터·섹션·스티커·이미지·스탬프·자유 그리기·댓글), dimensions(위치·크기·회전), paths(커넥터 시작·끝·꺾임), zindex(순서). 시제품 SVG로 단순 보드는 원본과 거의 같게 그려짐을 확인했다.

**범위 (결정 2026-11-06)**: 사용량이 있으므로 둘 다 **1차 이관·읽기 전용 보기 → 2차 편집**으로 지원한다. 데이터베이스 편집(GIRA-73)은 이관 뒤 우리 JSON 모델을 고치는 일이라 난이도 중간. 화이트보드 편집(GIRA-74)은 직접 만들면 난이도가 높아, 오픈소스 Excalidraw(MIT)로 원본 표본을 변환해 모양·손실을 먼저 평가하고 채택 여부를 정한다(너무 어려우면 보기 전용에 머문다). 실시간 공동 편집은 범위 밖.

**작업 방식 (결정 2026-11-06)**: 전체 이관이 아니라 **샘플 문서만** 가져와서 구현·검증한다 — 매크로별 예시 문서는 조사 자료(`macro-samples.json`), 데이터베이스·화이트보드는 스냅샷 도구. 조사 도구와 로컬 자료 안내는 `scripts/research/README.md`.

### HTML 블록 보안 원칙

HTML Macro Pro·html·iframe 매크로는 사용자가 넣은 임의 HTML·스크립트다. 항상 `sandbox` iframe(allow-scripts·팝업만, **allow-same-origin 없음**)에서 그려, 블록 안 코드가 Gonfluence 쿠키·API·부모 문서에 닿지 못하게 한다. 외부 CDN 로드는 허용(원본도 그렇게 동작), 내부망 주소를 가리키는 iframe 허용 여부와 CSP frame-src 목록은 구현 때 문서화한다.

## 정식 출시 후 고도화

- **관리자 통계**: 사용량, 사용자별 이슈 처리·문서 생성 개수, 활성률(DAU/WAU, 팀별 활동) 등을 조회. 자체 화면 대신 Grafana 같은 BI 도구를 PostgreSQL에 읽기 전용으로 붙여도 된다.
- **개인 대시보드**: 사용자가 저장 필터·쿼리 결과를 카드로 모아 구성하는 맞춤 대시보드. 카드 내용은 본인 접근 권한 범위로만 채워진다.
- **상위 이슈 상태 자동 전환 (구현 방식 미정)**: 하위 이슈 상태에 따라 에픽·상위 이슈 상태를 맞춘다. Jira도 기본 동작이 아니라 자동화 규칙(하위가 진행 중이면 상위도 진행 중, 하위가 모두 완료면 상위도 완료)으로 켜는 기능이다. 초안은 시작은 자동, 완료는 확인 후, 프로젝트별 켜고 끄기(이관 프로젝트는 원본 동기화와 충돌하므로 기본 끔). 규칙을 고정 기능으로 둘지 일반 자동화 규칙 엔진으로 만들지는 더 검토한다.
- **Gonfluence 문서 순서 끌어 바꾸기**: 알파는 사이드바 트리에서 문서를 다른 문서·폴더·스페이스 위에 놓아 그 아래로 옮기는 것까지 한다. 같은 단계 안에서 순서를 바꾸는 것(사이에 놓기)은 서버의 형제 순서(position) 관리가 필요해 고도화로 둔다.
